# Deployment

Production deployment guide for a single VPS (Ubuntu 22.04/24.04 tested
approach; any host with Docker 24+ works).

## 1. Prerequisites

- A VPS with at least **1 GB RAM** (2 GB recommended), a public IP, and a
  domain name pointing at it (A record).
- Docker Engine 24+ **with the Compose plugin**:

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER"   # log out and back in
docker compose version            # verify
```

## 2. Install (scripted)

```bash
git clone https://github.com/iRichNode/ai-vendor-outreach-platform.git
cd ai-vendor-outreach-platform
sudo bash scripts/install.sh
```

`scripts/install.sh` checks prerequisites, generates `.env` from
`.env.example` (with a random `SECRET_KEY` via `openssl rand -hex 32`), then
runs `docker compose up -d --build`. At the end it prints service status and
the URLs to check.

> **Important**: after install, edit `.env` and set real values — at minimum:
> - a strong `SECRET_KEY` (already generated by the script — verify it was)
> - `POSTGRES_PASSWORD` (the script leaves the default)
> - `BASE_URL` = `https://your-domain`
> - your integration keys (OpenRouter, Gmail, Telegram) as needed

Then recreate with new settings:

```bash
docker compose up -d --build
```

## 3. First boot

1. `docker compose ps` — all services should be `healthy`.
2. `curl -s http://localhost/health` → `{"status":"ok",...}`
3. `curl -s http://localhost/ready` → 200 `{"status":"ok",...}` (verifies DB + Redis)
4. Open `http://your-server-ip/` — the setup wizard creates the first admin.
   Alternatively set `INITIAL_ADMIN_USERNAME/PASSWORD/EMAIL` in `.env` before
   first boot (all three together) and the first API start creates the admin.

## 4. HTTPS with Let's Encrypt

The reverse proxy has a commented 443 listener in `docker-compose.yml`.
Enable it as follows:

1. Uncomment the `443:443` port mapping and the `./infra/certs` volume mount
   in `docker-compose.yml`.
2. Create `infra/certs/` and obtain certificates:

```bash
mkdir -p infra/certs
sudo apt install -y certbot
sudo certbot certonly --standalone -d your-domain \
  --config-dir infra/certs/config --work-dir infra/certs/work \
  --logs-dir infra/certs/logs --agree-tos -m you@example.com
# Deploy style: certbot fullchain.pem + privkey.pem at infra/certs/live/your-domain/
```

3. Add a server block in `infra/nginx/conf.d/default.conf` (or a new file in
   that directory) that terminates TLS and proxies to the same upstreams:

```nginx
server {
    listen 443 ssl;
    server_name your-domain;
    ssl_certificate     /etc/nginx/certs/live/your-domain/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/live/your-domain/privkey.pem;

    location /api/ { proxy_pass http://api:8000; proxy_set_header Host $host; }
    location /     { proxy_pass http://frontend:3000; proxy_set_header Host $host; }
}
```

4. Recreate the proxy: `docker compose up -d --build reverse-proxy`.
5. Set `BASE_URL=https://your-domain` and `COOKIE_SECURE=true` in `.env`
   (the compose default is already `true`) and restart: `docker compose up -d --build api frontend`.
6. Optionally forward port 80 → 443 for redirects and renew via a cron job
   (`certbot renew` needs the standalone server stopped, or use the webroot
   method through nginx).

## 5. Updates

```bash
git pull
docker compose up -d --build
docker image prune -f          # remove old images
```

Migrations run automatically on API container start (Alembic `upgrade head`;
disable with `SKIP_AUTO_MIGRATE=1` if you manage migrations yourself).
Back up first — see [backup.md](backup.md).

## 6. Backups & monitoring

- Install a nightly backup cron (see [backup.md](backup.md)) and copy the
  `backups/` directory off-site.
- Monitor `/ready` from outside the stack (e.g. Uptime Kuma or a cron curl):

```bash
*/5 * * * * curl -fsS https://your-domain/ready >/dev/null || logger -t outreach "ready check FAILED"
```

- Watch logs: `docker compose logs -f api worker scheduler`

## 7. Scaling notes

- One VPS runs the whole stack today. If send volume grows:
  - Raise `GUNICORN_WORKERS` (API) — keep workers × threads modest on 1–2 GB.
  - Start additional `worker` replicas via
    `docker compose up -d --scale worker=2` — SKIP LOCKED keeps them safe.
  - Tune `DISPATCH_INTERVAL_SECONDS`, `SCHEDULER_INTERVAL_SECONDS` and pacing
    variables instead of raising concurrency: this app is intentionally paced.

## 8. Troubleshooting

| Symptom | Likely fix |
|---|---|
| `/ready` returns 503 `degraded` | Check Postgres/Redis health; look at the `problems` array in the response |
| `api` never becomes healthy | `docker compose logs api`; check `SECRET_KEY` is set (compose fails fast if not) |
| Frontend shows API errors in browser console | Wrong `NEXT_PUBLIC_API_URL` baked at build; rebuild with `NEXT_PUBLIC_API_URL=/api` |
| Gmail OAuth token lost | It lives in the `appdata` volume (`/srv/app/data/gmail_token.json`); restore from your appdata backup |
| Migrations run twice | They are idempotent (Alembic version table); safe |
| `docker compose up` complains `SECRET_KEY` | `.env` missing or variable empty — `cp .env.example .env` and generate a key |

## 9. Security checklist (summary)

Full details in [security.md](security.md):

- [ ] `SECRET_KEY` set to a random 64-hex value, never committed
- [ ] `POSTGRES_PASSWORD` changed from the default
- [ ] HTTPS enabled and `BASE_URL`/`COOKIE_SECURE` correct
- [ ] `DEMO_MODE=false` and `ENVIRONMENT=production`
- [ ] Only port 80/443 open to the public
- [ ] Nightly backups + off-site copy verified by a test restore
